# SwoleMate Codebase Audit — 2026-06-11

Read-only audit of the `development` branch (HEAD `49b2f7d`, v3.1.1). No source files were modified; this report is the only artifact created.

---

## Executive summary

**Overall health score: 7.5 / 10**

This is a well-engineered self-hosted app, clearly above the bar for hobby projects. The Rust backend has serious security work in it (Argon2id, hashed session tokens, dummy-verify against user enumeration, CSRF origin checks, per-IP and per-user login throttling, scoped MCP tokens, PKCE-S256-only OAuth, distroless non-root container). The frontend is a disciplined SvelteKit SPA with a thoughtful offline story. Both test suites exist and pass (client: 130/130 unit tests; server: ~105 integration tests in `server/tests/api.rs`).

The weaknesses are operational and around the edges: a config-precedence footgun, an nginx header-inheritance bug that silently drops the CSP on HTML, a backup-restore flow that skips schema migrations, no CI, and an admin-lockout path.

**Top 5 highest-priority issues**

1. **(SEC-1, Medium)** nginx `add_header` inheritance bug — security headers (including CSP) are *not* sent on HTML responses because `location /` declares its own `add_header`.
2. **(BUG-1, Medium)** `server.env` values override real environment variables (`std::env::set_var` unconditionally in `find_env_file`), inverting the conventional precedence — Docker `environment:` entries are silently ignored.
3. **(BUG-2, Medium)** Backup restore does not re-run schema migrations — restoring a backup taken on an older schema leaves the live pool pointed at an outdated schema until restart.
4. **(BUG-3, Medium)** `POST /api/admin/users/{id}/disable` has no last-admin/self guard — the sole admin can disable themselves and permanently lock everyone out of admin functions (delete has the guard; disable does not).
5. **(OPS-1, Medium)** No CI at all — no `.github/workflows`, so the 100+ server tests, 130 client tests, lint, and `svelte-check` only run when someone remembers to.

**Production-ready?** Yes, for its stated scope (self-hosted, single household, behind the bundled nginx). The auth and data-isolation fundamentals are sound. I would fix SEC-1, BUG-1, and BUG-3 before calling it done, and add CI before the next release.

**Biggest risk area:** Operations — the backup/restore lifecycle (migrations, live-pool swap, no offsite copy, no healthchecks) is the most likely place to lose data or have a bad day, not the request-handling code.

## What's notably *good* (so it doesn't get refactored away)

- **Auth design**: tokens stored only as SHA-256 hashes (`auth/mod.rs::hash_session_token`); Argon2id with sane params; `verify_dummy_password` + uniform 200ms sleep against user enumeration; per-user lockout (`locked_until`) *and* per-IP throttling; sessions revoked on password change/disable; rotation near expiry with compare-and-swap on the old hash.
- **Authorization**: every workout/template/exercise query is scoped `WHERE id = ? AND user_id = ?` at the SQL layer (`db/workouts.rs` etc.) — no reliance on handler-level checks. All SQL is parameterized; no injection surface found.
- **Backup filename handling**: `routes.rs::is_safe_backup_filename` correctly blocks traversal (`/`, `\`, `..`, charset allowlist) before any filesystem join; tar extraction only unpacks three fixed entry names.
- **OAuth/MCP**: PKCE S256 mandatory, redirect URIs validated against registration (https-only except loopback http, no fragments/userinfo, `javascript:`/`data:`/`file:` banned), authorize page HTML-escapes all reflected values, disabled users/clients checked on every token lookup.
- **Containers**: distroless static non-root server image, `user: "1000:1000"` in compose, backend not published to the host, JSON body limits, per-class concurrency semaphores with timeouts.
- **Service worker**: deliberately never caches `/api/*` (auth-data-leak aware), network-first navigations, immutable-asset cache-first.

## Larger refactors (in priority order)

1. **Split `SessionExercise.svelte`** — the only file I'd call risky to change. The controller/actions layer is already well factored; the view layer hasn't caught up.
2. **Adopt `sqlx::migrate!`** for new migrations; freeze `schema.rs` as legacy.
3. **Collapse `api.ts`** onto a single typed request helper.
4. **Unify DB-path parsing** (`main.rs` and `backup.rs` both hand-parse `DATABASE_URL`) and pool configuration (startup vs post-restore) into shared functions.

## Security priorities

1. SEC-1 (CSP actually delivered) → then SEC-4 (tighten `connect-src`).
2. BUG-3 (admin lockout is an availability/security hybrid).
3. SEC-3 (gate `X-Real-IP` trust) — cheap insurance against future deployment changes.
4. SEC-5 (rate-limit `/oauth/register`) before exposing the instance more publicly.
5. SEC-2 (remove the plaintext credentials file).

## Testing priorities

Current state: strong for the project's size — 37 client test files / 130 passing unit tests covering the today-controller, offline queue, and API client; ~105 server integration tests in a single 5,067-line `server/tests/api.rs`. Gaps, highest value first:

1. **Backup/restore round-trip with an older-schema fixture** (would have caught BUG-2).
2. **Admin lifecycle tests**: last-admin disable (BUG-3), self-targeting operations.
3. **An nginx/deployment smoke test** (header presence, proxy paths) — even a shell script run in CI against the composed stack; nothing today exercises `nginx.conf` (would have caught SEC-1).
4. **Restore-under-concurrency** test (BUG-6).
5. Splitting `tests/api.rs` into modules — not coverage, but it's becoming hard to navigate.
6. No E2E suite (Playwright artifacts suggest it was removed); a 3-scenario happy-path E2E (login → log session → see it in history) would protect the core flow.

## Questions / assumptions

- **Assumed single-instance, household-scale deployment** behind the bundled nginx on a LAN (per `docker-compose.yml` using a `192.168.x.x` private registry). Several "Low" ratings (SEC-3, SEC-5, OPS-4, PERF-1) become Medium if the instance is internet-exposed for multiple tenants. `CORS_ALLOWED_ORIGINS=https://test.battercloud.cc` in `server.env` suggests at least partial public exposure — worth confirming.
- **`allow_dynamic_client_registration`**: I did not verify its default value in `oauth/mod.rs`; if it defaults to *on*, SEC-5 moves up. Needs verification.
- **Backup "download" feature**: assumed the README is stale rather than the endpoint being lost in a refactor — worth a quick `git log` check on `routes.rs` if you remember shipping it.
- I did not run `cargo test`/`cargo clippy` (full Rust compile not exercised in this session); server test pass-rate is asserted from the suite's presence and recent commit history, not a fresh run. Client tests were run fresh: **130/130 pass** (`npm run test`, 26.6s).
